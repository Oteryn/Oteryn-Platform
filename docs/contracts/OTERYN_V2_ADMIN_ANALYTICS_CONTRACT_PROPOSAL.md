# Oteryn-v2 ADMIN game analytics feed

## 1. Purpose, authority and limits

Proposal ID: `oteryn-v2-admin-analytics-proposal-1`. Date: 2026-11-07. This proposes a bounded, aggregate-only Game → Platform feed for the authenticated admin panel. It is **not part of public projections** and does not extend their routes, family enums, watermark or exposure permissions.

Owner decision, 2026-11-07, relayed by the Game coordinator: **Game will implement the producer once this proposal is accepted. Game's durable aggregates retain per-creature-key and per-world dimensions; only the public wire is aggregated.** An existing public total must not be mistaken for the complete Game aggregate schema or used to justify discarding dimensions. This ADMIN wire may carry the retained world/creature breakdowns subject to suppression. It does not authorize adding those breakdowns to the public wire.

Game owns source truth, counting, cohort qualification, durable aggregation, corrections and replay. Platform owns strict ingestion, disposable admin read models, RBAC, audit, retention enforcement and presentation. Acceptance belongs to the game owner through the coordinator. Proposal acceptance, producer delivery, consumer qualification and production activation are separate gates. This document implements none of them and authorizes no Game change, gameplay mutation, shared SQL, deployment or collection from a restricted-purpose audit source.

Revision 1 excludes player drill-down, identities or pseudonyms, hunt logs, raw session intervals, location/channel breakdowns, live surveillance, arbitrary SQL, security investigation, automatic enforcement, wallet/premium currency and public statistics/rankings. Admin access to this feed grants no access to private journals or identity re-linking.

## 3. Bounded metric set and counting semantics

All bucket intervals are half-open UTC `[start,end)`: day = 86400 seconds aligned to midnight, hour = 3600 seconds aligned to the hour. They are reporting intervals, independent of the Game world-reset calendar. Event time is Game's authoritative committed time; Game normalizes receipt timestamps in milliseconds/microseconds by flooring to Unix seconds once, before bucketing or integrating ONLINE transitions. Thus concurrency is exact under this one-second accounting resolution, not subsecond precision. Arrival time never selects a bucket. No arbitrary filters or extra dimensions are accepted in revision 1.

Retention below applies to both the proposed Game **replayable aggregate** and Platform read model from bucket end, including corrected/suppressed buckets. It does not prescribe deletion of underlying Game authority receipts or adopt their retention for analytics.

| Family / metric | Dimensions and granularity | Proposed retention | Durable grounding / delivery classification |
|---|---|---|---|

| `boss_kills_daily`: `kills` | `WorldId × creature_key × UTC day`; boss subset of the preceding family, classified at occurrence time | 400 days | S4 provides credit/classification evidence, not physical counts. **requires new Game aggregation** with occurrence deduplication and historical world/time; no multiplication by credited characters. |

| `level_distribution_daily`: `characters` | `WorldId × level_bucket × UTC day`; one end-of-day stock snapshot, not summed level-up events | 400 days | S8 grounds current level/world. **requires new Game aggregation** for a consistent historical cut, lifecycle eligibility, missing-level handling and cohort-safe buckets. |

Fixed level buckets: `1_7`, `8_19`, `20_49`, `50_99`, `100_199`, `200_499`, `500_999`, `1000_plus`, `unknown`. Boundaries are inclusive; `unknown` is missing/unclassifiable progression, never level 1 by default. Count each eligible, active character in exactly one bucket at the committed cut immediately before day end, using its world at that cut. Exclude deleted/detached characters according to Game lifecycle authority; hidden public profiles are not silently dropped from admin population counts. This eligibility definition needs owner acceptance.

For activity, an ONLINE transition starts an analytics session; reconnect without leaving ONLINE does not add a session. Leaving ONLINE closes it; entering again starts another. Channels do not create extra characters. Game clips intervals at hour boundaries and world transfers; crash closure occurs only on the authoritative lease-expiry/reconciliation commit, with no Platform extrapolation. `online_character_seconds` integrates ONLINE character occupancy over the full hour. `avg_online_milli = floor(1000 × online_character_seconds / 3600)`; this is fixed-point thousandths of a character, not a floating point value. `peak_online` is the maximum simultaneous ONLINE count over that hour, not the largest observed sample. Require `0 <= avg_online_milli <= 1000 × peak_online`, using checked arithmetic. No hour is complete while an unresolved transition could alter it.

Creature kills are the deaths of those creatures, not a second additive death metric. They include boss kills; **do not add boss counts to creature counts**. Count physical deaths once across parties, channels, producer retries and recovery; bestiary bonuses do not add deaths. Exclude despawn, reset cleanup and summoned companions unless the owner accepts a different versioned eligibility rule. Boss classification uses the occurrence's Game content definition; unknown classification blocks completeness instead of guessing from a display name. Game retains creature/world keys and classification provenance internally even when a public total omits those keys. Corrections replace whole bucket snapshots at a higher revision, never increment counts on delivery.

**Economy is excluded from revision 1.** S9 does not establish the candidate's required existing world/day aggregate. Gold in/out per world/day **requires new Game aggregation** and approved source coverage; it cannot be manufactured from wallet balances, bank transfers, loot values or a subset of fee receipts. A later revision must separate mint/burn from transfers, define currency units/refunds and classify every included source. If accepted later, propose UTC-day granularity and 400-day aggregate retention, subject to its own owner decision. No economy family/route member is accepted by the closed enum here.

## 4. Who may see it: RBAC, privacy and audit

Propose dedicated Platform permissions `admin.analytics.view` and `admin.analytics.export`, initially assigned **only to the built-in `platform_admin` role**. Require authentication, confirmed MFA, `admin.access`, active administrator membership and `admin.analytics.view` on every page, JSON read, chart request and export download; export additionally requires `admin.analytics.export`. Do not infer access from `game.analytics.read`, public-statistics permissions, support/GM status or possession of an internal URL. Server-side role editing must prevent these permissions being granted to non-admin/custom analyst roles; effective grants and revocations are checked at each request, not just navigation. These are proposed policy/catalog changes for implementation, not shipped permissions.

Every successful view and export, and every denied attempt, creates a durable access audit entry through the Platform audit boundary. Record authenticated staff actor (only in the protected Platform audit store), request ID, action, bounded family/world/bucket selection, result, source epoch/revision, privacy-policy revision and export row count/digest where applicable. No aggregate values, response body, player data or free-form filters enter audit metadata. Write the successful-read audit before releasing data; audit failure denies the read/export. Include pagination, cached responses and downloads, with audit correlation for asynchronous exports. Audit storage is separate from the analytical dataset; propose 400-day access-audit retention, access only through the existing audit permission, with production retention policy still requiring approval.

**Minimum cohort: five distinct Game accounts per positive cell.** Game evaluates distinct contributing accounts internally, never exports the IDs or exact small cohort size, and sends only a suppression state. For kills/bosses use participating accounts for the counted occurrences; deaths use victim accounts; creations use creating accounts; activity uses accounts contributing ONLINE occupancy; level buckets use accounts owning counted characters at the snapshot cut. Multiple characters/sessions from one account do not satisfy five accounts. Unprovable account attribution means suppression. Zero is allowed only when positively proven complete and safe under the same disclosure policy; absence of evidence is unavailable, not zero.

Apply suppression **before transmission**, again on every Platform serve/cache/export boundary, and to all values of an activity row together. Cells with 1–4 accounts, unknown qualification or unsafe disclosure carry `state:"suppressed",values:[]`. Use complementary suppression: withhold totals/other cells that would let subtraction recover a suppressed cell. Check fixed buckets across dimensions, releases and revisions; a correction must not reveal a change attributable to fewer than five accounts. If Game cannot prove that release/difference safety, withhold the affected bucket and related totals. No arbitrary regrouping, top-N, cross-world totals, overlapping custom windows or query joins that bypass suppression. No claims that k=5 alone proves anonymization; the owner must accept the remaining aggregate disclosure risk.

Publish only complete closed buckets, **at least 24 hours after bucket end**, on a fixed release schedule. No provisional/intrahour admin graph in revision 1. This reduces schedule inference and repeated-query differencing; it does not replace cohort/complementary suppression. Small worlds or rare bosses can legitimately remain suppressed. The panel distinguishes suppressed, unavailable, expired and confirmed zero without exposing a small sample count.

Exclude AccountId, CharacterId, AnalyticsActorId, names, email, addresses/IPs, device/network data, session/admission/connection IDs, positions, channels, node/instance topology, receipt/command/transaction bindings, credentials and private journal payloads. `WorldId` and Game catalogue `creature_key` are the only entity dimensions crossing this feed. No public page, public API, search, CDN, sitemap, public projection cache or player export consumes these rows. Responses use `Cache-Control: no-store, private` and `Pragma: no-cache`. No analytics third-party beacon or public object-storage link receives data. Operational logs contain only family, operation, result class and timings, without bodies or entity IDs.

## 5. Transport and proposed wire

### 5.1 Direction and trust

Choose **push, Game → Platform**, to deliver durable aggregate snapshots and watermarks from a transactional outbox without exposing a Game listener or coupling page rendering to Game availability. Platform initiates no Game HTTP/SQL request. This matches plan §5.3.2, Store wire and S10. A Platform-pull design would be a **new architectural direction**, requiring explicit owner approval and a new Game query/listener contract; it is not an implicit fallback here.

Propose a separate purpose-scoped mTLS identity/allowlist for `game-admin-analytics`, distinct from public projections, Store, commands, runtime evidence and general admin-control agents. Use HTTP/1.1 over TLS 1.3 with server verification, verified client certificate identity mapped to exactly one configured source authority, a new connection per exchange and `Connection: close`. Identity comes only from the verified TLS connection/trusted adapter; browser-supplied forwarding headers never establish it. A public-projection or admin-control certificate cannot publish analytics merely because it is otherwise trusted. SHA-256 below compares bytes; it is not authentication or a signature. No new HMAC/bearer token is proposed.

### 5.2 Encoding, types and snapshot members

Canonical JSON follows Store conventions: exactly the specified members in the listed serialization order, compact UTF-8 object with no BOM, no trailing newline, no insignificant whitespace, and no duplicate/unknown/missing/null members, floats, implicit coercion or unnecessary escapes. Strings here use bounded ASCII. Re-encoding with unescaped slashes/Unicode must reproduce exact bytes. Maximum nesting is five containers. `Content-Type: application/json`; no `Transfer-Encoding`; `Content-Encoding` absent or `identity`. Validate actual bytes as well as canonical decimal `Content-Length` when supplied. Empty/malformed/oversized bodies return `400` on this proposed feed. This follows the later statistics-proposal oversize convention; it does not rewrite Store's separately specified `413` cases.

`contract_version` is JSON number `1`; all other integers/timestamps are canonical decimal **strings** (`0` or `[1-9][0-9]{0,19}`, checked to u64). Epoch/revision and nonzero times are 1..u64::MAX. Unix timestamps are seconds UTC, never milliseconds. `world_id` is canonical lowercase non-nil UUIDv7. `source_authority` matches `[A-Za-z0-9._:/-]{1,128}` and the configured peer. `creature_key` is a case-sensitive Game catalogue key matching `[A-Za-z0-9][A-Za-z0-9_./:-]{0,511}`; unrepresentable keys block the family pending a version decision, never truncate or normalize. `hex64` is lowercase SHA-256. Arithmetic/expiry overflow is invalid.

The closed `family` enum is precisely the six metric families in §3. No new public-projection family is introduced. A snapshot subject is `(source_authority,family,world_id,bucket_start)`; `bucket_end` is derived from the family interval and validated. All pages and commit for one revision agree on all common fields. `privacy_policy_revision` is a 1..64-byte `[A-Za-z0-9._-]+` identifier of the accepted suppression/release rules, matched against Platform's current privacy floor; unknown or older policy denies serving. `source_observed_at` records Game's observation when constructing the frozen release, not the historical bucket cut. Require `bucket_end+86400 <= source_observed_at <= platform_now+2`, and independently enforce the release delay at every serve.

Page members, in order: `contract_version`, `operation`, `source_authority`, `family`, `world_id`, `bucket_start`, `bucket_end`, `analytics_epoch`, `snapshot_revision`, `source_observed_at`, `privacy_policy_revision`, `page_index`, `page_count`, `rows`.

- `page_count` is 1..64; `page_index` is 0..page_count−1. Each page has 0..128 rows; only a single-page empty snapshot may have zero rows. Total snapshot bound: 8192 distinct rows and 8 MiB page bytes. Rows have exactly `key`, `state`, `values`, in that order. Sort rows strictly by ASCII key across page boundaries; no duplicates, omissions or arbitrary top-N truncation.
- `key` is creature key for the two kill families; for player deaths a creature content key or the literal `player` or `unknown`; literal `world` for activity/creations; one of the nine fixed level bucket names for level distribution. Activity and creation families have exactly one row; level distribution exactly nine, sorted by key; player deaths enumerate every attributed killer key present in the bucket, plus `player` and `unknown` whenever their counts are non-zero or suppressed. Kill families enumerate the complete Game catalogue eligibility set at that bucket's cut, including safe zeros and suppressed keys, or refuse completeness. Missing keys are never inferred as zero.
- `state` is `visible`, `suppressed` or `incomplete`. `incomplete` marks a cell whose Game source coverage has a gap (§10 decision 2); it is never backfilled or shown as zero. `values` is empty for suppressed and incomplete; otherwise it is an ordered array of decimal strings: `[kills]`, `[deaths]`, `[sessions_started,online_character_seconds,peak_online,avg_online_milli]`, `[created]` or `[characters]` according to family. No omitted value or negative count. Page data is complete closed-bucket data only; no partial-count field.

Commit members, in order: `contract_version`, `operation`, `source_authority`, `family`, `world_id`, `bucket_start`, `bucket_end`, `analytics_epoch`, `snapshot_revision`, `source_observed_at`, `privacy_policy_revision`, `state`, `row_count`, `page_digests`. `state` is `replace` or `erase`; `page_digests` is the ordered array of exact canonical page-body SHA-256 digests. `replace` binds 1..64 pages and their total row count; digest-array length must equal every page's `page_count`. `erase` has `row_count:"0",page_digests:[]` and removes the entire subject while retaining its fence. A known-empty kill eligibility set is a one-page empty replacement, not erasure and not proof of zero for unlisted creatures. The consumer stages pages off-path and exposes a replacement only after the commit verifies all pages, digests, row coverage, privacy and bounds atomically. A page acknowledgement means durable staging, not visibility. Apply restrictive corrections to released data immediately after verification; do not wait for the next scheduled release.

Watermark members, in order: `contract_version`, `operation`, `source_authority`, `family`, `world_id`, `analytics_epoch`, `privacy_policy_revision`, `complete_through`, `observed_at`. This is delivery completeness for all changes eligible for release through that Game cut, including corrections/erasures; the 24-hour embargo is not permission to skip an already due bucket. Heartbeats cannot advance completeness past a missing commit or unresolved source/classification/privacy failure. Historical bucket end is not the freshness clock.

### 5.3 Idempotency, epochs and resync

Game freezes subject/revision and exact page/commit bytes in a durable outbox before first delivery. The idempotency key is `(subject,analytics_epoch,snapshot_revision,page_index)` for a page and `(subject,analytics_epoch,snapshot_revision)` for commit. Equal key/equal bytes is accepted without reapplying; equal key/different bytes is `409`, retaining the first evidence and alarming. Order committed snapshots lexicographically by numeric `(analytics_epoch,snapshot_revision)`: lower is `superseded`, higher replaces atomically. Revision gaps are legal full replacements, not delta continuity. A timeout after commit is retried under the same identity/bytes; delivery never replays gameplay effects. Game retains every page until a valid commit acknowledgement (`accepted` or `superseded`), so expired staging can be replayed exactly. Only then may it clear that outbox revision, preserving concurrent newer work. Durable rollups remain available for the full retained resync window.

Propose a **dedicated analytics epoch and durable external high-water fence**, coordinated with Game restore but independent of public projections, Store and admin-agent ownership epochs. Only a Game operator's reconciled restore/resync raises it, strictly above the surviving external fence. Platform persists the maximum epoch outside disposable generations; rejects lower epochs; a higher authenticated epoch immediately makes every older analytics family unavailable. Missing/ambiguous restore-fence evidence disables publication/serving. Heartbeats, process restart and consumer rebuild cannot invent or reset an epoch.

Full resync is operator-driven **Game push**, not a new Platform-callable Game route. At an operator-established epoch/cut, Game enumerates every retained family/world/bucket subject, all pages and erasures, and a coverage manifest including empty worlds/families and the complete retained range. The bounded manifest must bind sorted subject/revision/page digests and prove absence for previously stored subjects. Platform builds a new generation off-path, validates the manifest, retained coverage, current privacy/expiry rules and the outbox tail through that cut, then switches atomically with a fresh watermark. A watermark alone cannot certify an empty rebuilt database. An initial baseline uses the same proof.

The exact manifest/control envelope is an **acceptance blocker requiring shared fixtures**, not an undocumented fourth delivered operation. Propose chunked push through a separately accepted resync operation: at most 128 subjects/64 KiB per manifest chunk, immutable cut, ordered chunk digests, explicit terminal digest/count and disk-streamed verification. No unbounded in-memory list, inferred completion or hand-replayed packet captures. Keep presentation disabled until that envelope and measured retained-set replay are accepted and qualified; live ingestion alone is insufficient. Within-epoch repaired generations still need manifest coverage; restore with lost source/fence continuity requires a higher epoch. Game must report an unavailable retained range explicitly rather than reconstruct it from bestiary counters or current levels. A 400-day replay promise requires persisted rollups, not just surviving raw inputs.

## 6. Freshness, failure modes and resource limits

Proposed testing/preproduction defaults: watermark target every 30 seconds, maximum valid age 120 seconds, future-clock tolerance 2 seconds; `complete_through <= observed_at <= platform_now+2`. Use checked comparisons at every page/chart/export/cache read. Watermark regression is ignored as superseded; equal cut with conflicting evidence alarms and denies the affected scope. A fresh watermark cannot override incomplete resync, an old epoch, invalid privacy evidence, a missing due bucket or retention expiry. On any such condition the affected scope is **unavailable**, not zero, offline, empty or a last-known-good numeric graph. No stale display grace or synchronous Game fallback. Production cadence/skew/SLA remains an owner decision.

| Result | Required action |
|---|---|
| `200` canonical `{"contract_version":1,"result":"accepted"}` | Durable idempotent staging/commit/watermark acceptance according to operation; no gameplay effect claimed |
| `200` canonical `{"contract_version":1,"result":"superseded"}` | Older evidence safely ignored; never lowers a fence |
| `400`, empty | Malformed/unsupported/oversized, impossible bucket/value or schema/coverage violation; no mutation |
| `401`, empty | Wrong/missing purpose peer or source authority; no mutation |
| `409`, empty | Conflicting identity/bytes; preserve first record, alarm and withhold affected scope |
| `429`, empty | Rate limited; canonical `Retry-After` seconds at least 1; retain outbox |
| `503`, empty | Disabled, configuration/authority ambiguous, database/audit unavailable, staged pages missing or dependency unavailable; no claimed acceptance |
| Timeout, TLS/network failure, unknown status or invalid/oversized response | Outcome unknown, possibly committed; retain and retry exact bytes/identity |

Response ceiling 256 bytes. Connect ceiling 1 second, handshake 2 seconds, whole exchange including setup 5 seconds. One snapshot in flight per family/world; global maximum four exchanges and two staged generations per subject. Proposed rate limit 1200 requests/minute per peer, configurable only within 1..6000 after measured qualification. Stage on bounded storage; expire abandoned uncommitted staging after 24 hours and allow exact replay. Never evict an acknowledged visible snapshot to make staging appear successful. Retry transient failures exponentially 1..60 seconds, honoring larger `Retry-After`; definite `400`/`401`/`409` holds at least 300 seconds and alerts. Backlog disk caps/alarms must be measured; capacity refusal stalls completeness, never truncates or silently drops retained rollups.

Revision-1 deployment envelope: at most 256 registered worlds and 8192 eligible creature keys per kill bucket. Exceeding a bound blocks that scope pending a new accepted capacity/version decision. Verify complete retained-set resync capacity before enabling 400-day retention; no inherited claim that G-8's proposed 60-second resync target is achievable here. ## 7. Platform read model, retention, deletion and panel

Store only accepted aggregate subjects/pages, committed rows, provenance/digests, coverage manifests, watermarks, epoch/privacy fences and ingestion receipts in an admin-only schema/role. Use partitioned time buckets and indexed `(authority,family,world,bucket,key)` access. A transactional generation switch exposes no mixed revisions. Preserve suppression metadata; do not persist underlying player/session/cohort membership. Platform does presentation formatting and bounded selection, not recomputation of Game truth or new unqualified cross-cell analytics. The existing opaque `analytics_cache` requires a typed, versioned consumer before reuse; it is not historical authority.

Expire activity at 30 days and daily aggregates at 400 days from bucket end on **both** producer replay and consumer serving. Enforce expiry at read time during outages, purge payloads/caches/staging within 24 hours, and expire payload-bearing backups within 30 days of purge. Corrections do not restart retention. Minimal non-payload epoch/revision/privacy fences survive the supported replay window; keep a subject fence until its bucket is permanently expired or its entire epoch is fenced out. Replay/restore must reapply current time and privacy floors, preventing resurrection. Temporary quarantine holds only bounded reason/digest, not bodies, for at most seven days. These are proposed operational windows, pending owner/privacy approval.

Game sends higher-revision suppression/erase corrections when deletion or reclassification changes a released cohort. Platform immediately fences all affected generations/caches/exports and refuses reads if it cannot establish current eligibility. A privacy-policy revision has an independent Platform floor; a fresh Game revision never lowers it. Retained safe, non-identifying totals need not be rewritten merely because a public profile is hidden, but Game must reassess cohort and legal deletion obligations. Legal holds on source evidence belong to Game; no automatic extension of this analytical read model is implied. Full erasure, backup restoration and audit-record retention must be qualified before production.

Proposed admin-only pages: overview with delayed daily population/creation/death trends and freshness; creature/boss daily breakdown by world; hourly activity history with explicit UTC and exact concurrency definitions; daily level distribution with suppressed/unknown cells; and feed health showing coverage, correction state and retention boundaries. No player links or drill-down. Each response identifies data cut, epoch/revision, UTC range and freshness/suppression state without leaking private topology.

Exports are bounded CSV/JSON through the authenticated admin host only, with the same permission/cohort/freshness checks at creation **and download**. Proposed limit: one world/family, at most 31 days, 10000 rows and 8 MiB; refuse oversized results rather than truncate. No raw source payload, emailing, public link or public projection export. Suppressed rows remain suppressed. Export is **disabled at first activation** (§10 decision 4); enabling it later is a separate owner decision. Download artifacts expire after one hour; revocation/expiry/privacy change denies download and removes the artifact. Escape spreadsheet-formula-leading text in CSV. Audit creation and every download, and stream only after successful audit.

Shared statistical definitions may be reconciled with T65/T69/G-8, but public readers and public-family enums remain separate. This proposal neither edits the plan nor closes any task.
