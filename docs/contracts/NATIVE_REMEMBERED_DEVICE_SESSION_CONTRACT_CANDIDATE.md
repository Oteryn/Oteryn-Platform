# Native remembered-device session contract candidate

Status: **CANDIDATE — DISABLED BY DEFAULT — NOT APPROVED FOR PRODUCTION**.

This additive candidate addresses repeated browser redirects for the first-party Rust
client. It does not change the accepted OAuth flow, enable an endpoint, or grant rollout
authority. The existing `OTCLIENT_GAME_AUTH_CONTRACT.md` remains authoritative: first
authentication uses the system browser with Authorization Code + PKCE S256; OAuth
refresh tokens must not be persisted or used; issuing a ticket consumes the OAuth token
family. Embedded credential webviews and password grants remain prohibited.

The candidate introduces a **separate native remembered-device credential**, not a
Passport refresh token. It is usable only for the same Identity, canonical AccountId,
first-party Rust OAuth client, and original game/security generations. It cannot
authorize Canary/legacy login, web account management, MFA or recovery, arbitrary API
scopes, or character ownership supplied by the client. The first browser authentication
retains existing Identity login/MFA/security controls. Routine subsequent game entry can
then complete inside the client while this narrowly scoped device family remains valid.

## Authority and activation

`NativeRememberedDeviceSessions` requires strict Boolean
`game-auth.device_sessions.enabled === true` and environment `testing` or
`preproduction`. A missing key is false. This batch does not add
production activation or changes to existing ticket issuance. Additive candidate HTTP
adapters/configuration now exist, but every route refuses the default disabled state.
Production is refused even if an operator sets the feature key to true.

Enabling a future complete feature requires an owning contract/ADR and independent
security review covering the producer, consumer, credential storage, HTTP protection,
revocation, database concurrency, and real actor-to-game-entry result. Source, isolated
tests, or this document alone are not rollout or production-safety proof.

## Enrollment after first browser authentication

1. The client visibly offers an unchecked **Remember this device** choice. The device
   credential is requested only after explicit opt-in. Account/password/MFA entry stays
   in the external browser.
2. The normal PKCE exchange returns the existing short-lived `game:ticket` bearer.
3. An enrollment adapter calls `enroll(identity, accessTokenId, explicitConsent: true)`
   before existing ticket issuance consumes that bearer. The adapter uses the authenticated
   bearer identity and token ID, never a client-selected authoritative Identity or AccountId.
4. Under one transaction, the existing native OAuth verifier locks and revalidates
   Identity, OAuth token, original generation, scope, expiry, revocation and registered
   public-client policy. Only `nativeTicket === true` may enroll. Disabled/terminated
   identities and unavailable canonical/native security facts are denied.
5. One OAuth access token can enroll at most one family, enforced by a unique database
   constraint and serialized identity/token locks. A repeated request does not retrieve
   the original plaintext credential or create another family.
6. The server snapshots both `game_auth_generation` and `native_security_generation`.
   Both are retained for the entire family, never silently advanced to bypass revocation.
7. The service returns the sole plaintext credential and expiry metadata. The normal
   OAuth-to-ticket path remains unchanged and revokes its Passport family as before.

A lost enrollment response requires fresh browser authentication. Do not repeatedly
enroll with a stale bearer or retrieve a secret from a database/backup/log.

## Credential and retained state

The bearer is `otd1.` followed by unpadded base64url encoding of 32 bytes generated by
`random_bytes`: 256 bits of cryptographic randomness. Only its SHA-256 hash is stored.
Plaintext passwords, MFA codes, device secrets and Passport refresh tokens are not
persisted in these tables. A deterministic hash is appropriate for this randomly
generated high-entropy secret; password hashing remains framework-owned and unchanged.

`native_device_session_families` stores the Platform family UUID, Identity/canonical
AccountId/client binding, enrollment token ID, original generations, current sequence,
absolute/idle expiry, and terminal revocation facts. `native_device_session_credentials`
retains the unique credential hash, family UUID, sequence, issue time and consumed time.
All used hashes remain available to detect reuse of any predecessor, not merely the
immediately previous credential.

One database connection must contain Identity, Passport client/token and family state;
cross-connection configuration is refused. Migrations add tables without modifying
existing account/token/ticket data. Rollback refuses to drop any populated remembered
session history. Retirement/pruning is a separately authorized lifecycle change; this
foundation performs no purge or account/database reset.

Secrets are exported explicitly only by `IssuedDeviceSessionCredential::secret()` to
the TLS response adapter. DTO debug output is redacted and PHP serialization is refused.
Request/response logging, exception reporting, tracing and audit adapters must independently
redact all credential inputs and response bodies; DTO redaction does not make arbitrary
string logging safe. Methods receiving secrets use `SensitiveParameter`.

## Atomic rotation and bounded native result

`rotateAndUse(secret, oauthClientId, purpose, callback)` owns a standalone transaction;
an ambient outer transaction is refused. This prevents a caller from rolling back
terminal replay revocation after catching the refusal. Locator reads confer no authority.
Lock order starts with canonical Identity and continues through client, family and
credential, so account revocation and enrollment serialize with rotation.

Within the locks the service verifies:

- exact stored client binding and a currently valid first-party Rust public client;
- current Identity usability and immutable canonical AccountId;
- both original generations still exactly match current Identity generations;
- neither absolute nor idle deadline has been reached;
- family is not revoked, credential is unconsumed, and sequence is current.

The service consumes the old hash, creates exactly one new random successor, advances
sequence, and executes a trusted native-only callback in the same transaction. The
callback receives `VerifiedRememberedDeviceAuthorization` with immutable Identity ID,
canonical AccountId, client ID, original generations, family ID and one of:

- `NativeCharactersRead`: run the existing owner-scoped native character query;
- `NativeTicketIssue`: issue the existing bounded, single-use native Game Login Ticket
  for the locked canonical Identity.

The typed result is transaction-scoped authority, not a reusable access token. The
callback must not return this authorization object or use it after commit. It cannot
mint Passport tokens, add scopes, reinterpret a character's owner, or issue legacy tickets.
Ticket TTL, audience, single-use redemption and authoritative world admission remain
unchanged. Callback code may use database reads/writes only; no network calls, external
notifications, synchronous mail or other non-transactional effects are permitted.

The service uses Laravel's bounded transaction retry for database deadlocks (three
attempts). A rollback removes both rotation and native database effects before a safe
internal retry. This is not a retry of a successfully consumed network credential.

When a used predecessor is presented, the family is terminally revoked. Replay,
expiry and changed security context return denial **after the revocation commits**;
throwing inside that transaction would incorrectly roll it back. Unknown/malformed
secrets and wrong-client requests receive the same generic refusal and cannot revoke
an unrelated family. No callback is executed for a refused credential.

## Lifetime and concurrency semantics

Default maximum absolute lifetime is 30 days; default maximum idle lifetime is 7 days.
Configuration may shorten either limit, but cannot exceed those bounds or use non-integer
or non-positive values. Each successful use sets idle expiry to the earlier of
`now + idle TTL` and the original absolute deadline. Rotation never moves the absolute
deadline. Equality at either deadline is expired.

Two requests racing with the same credential serialize: at most one rotates and runs
its callback; a second committed use observes consumption and revokes the whole family.
An already issued short-lived ticket is still governed by its normal ticket/security
generation checks; family replay revocation does not retroactively invent a new ticket
revocation mechanism or forcibly disconnect an existing admitted game session.

The client must serialize remembered-device operations, including owner reads and
ticket issuance. Different concurrently running client processes must coordinate the
same stored credential or perform independent enrollment; a process-local mutex alone
does not solve cross-process reuse.

On an uncertain network outcome or credential-storage failure, the client clears its
local usable credential and returns to normal browser authentication. It must not
transparently retry a predecessor or accept an older delayed response. Consequently a
lost rotation response can require an extra browser login. This deliberate availability
tradeoff is preferable to a replay grace window or saving recoverable plaintext on the
server. Persisting the successor in the system credential vault must succeed before
starting the next remembered operation or using the returned ticket to enter the world.

## Logout, cancellation and account revocation

`revokeCredential(secret, clientId)` revokes that family idempotently. A used predecessor
may revoke its own family, allowing best-effort cancellation after an uncertain response;
it cannot refresh or authorize an operation. Unknown/wrong-client credentials get the
same generic denial. The client clears its local vault entry even when the server is
unreachable and must distinguish local removal from confirmed server-side revocation.

`revokeForOwner(identity, familyId)` locks and scopes the family to an authenticated
usable owner. A future browser adapter must retain existing Identity session checks,
CSRF, authorization and appropriate recent-authentication requirements. It must not expose
another actor's sessions. There is no unbounded actor/device-enumeration API in this batch.

Existing Identity game/native generation advancement prevents every old family from
authorizing its next operation; families do not adopt the new generations. Password,
MFA, recovery, logout-all, disable and termination flows must be qualified against their
existing owning revocation contracts. Do not claim a normal web logout or already-admitted
session is revoked unless that contract explicitly guarantees it.

Security review identified MFA confirmation as a concrete stale-authorization gap:
the previous confirmation action advanced only the web-session generation, so a device
enrolled before MFA could retain both original game generations and bypass the newly
enabled factor. The candidate includes a narrowly scoped correction in
`ConfirmIdentityMfaEnrollment`: after successful password/TOTP confirmation, the same
transaction calls the existing `RevokeIdentityGameAuthorizations` owner used by password
changes and MFA disable/reset. This advances both game/native generations, enforces the
existing native non-rollback witness when activated, and revokes old OAuth authorizations.
Prior device families fail their next current-generation check and require normal browser
authentication with the newly confirmed factor. Starting unconfirmed enrollment does not
advance these generations. The regression invokes the actual enrollment/confirmation
actions with a real TOTP rather than manually changing a generation field. This correction
does not by itself qualify the remembered-device feature for activation.

## HTTP and client integration requirements

The candidate HTTP adapters remain disabled with this feature, validate an exact versioned
request shape, reject client-selected authority fields, rate-limit enrollment/rotation/
revocation and apply the existing sensitive-response no-cache policy to success and failure.
Serve HTTPS in deployment. A bounded explicit localhost exception may support authorized
development only; remote plain HTTP must fail closed. Do not place device credentials in
URLs, query strings, fragments, referrers, browser cookies, diagnostics or crash reports.
No tunnel, Cloudflare change or client-installed networking component is required.

The client stores a secret only in the OS credential vault, keyed by exact trusted
Platform origin and public client ID. Metadata alone may be stored in ordinary settings.
Failing secure-vault access must disable remembering, never fall back to a JSON/env/text
file. First-time PKCE verifier/state and OAuth bearer remain transient. Existing browser
login remains available when remembering is disabled, expired, revoked or unavailable.

Suggested integration sequence (route names are selected by the owning adapter):

1. Enroll with authenticated PKCE bearer, explicit opt-in, and save returned credential.
2. Use the normal original bearer for first character listing/ticket issuance.
3. On later launches rotate for an owner-scoped character listing, save successor.
4. After character/world choice rotate for native ticket issuance, save successor.
5. Run the existing gateway/native admission flow with that ticket alone; never send the
   remembered credential to the Game Gateway or game node.
6. On logout/cancellation request family revocation and remove the vault entry.

### Candidate HTTP wire version 1

All four routes use POST and `Content-Type: application/json`. Bodies are bounded to
1024 bytes, flat JSON objects with the exact fields below. Duplicate keys (including
escaped spellings), unknown fields, query parameters, nested values, string versions,
non-Boolean consent, compressed/transfer-encoded payloads and inconsistent lengths are
refused. There are no caller-selected Identity/AccountId/generation/purpose fields.
The existing sensitive-cache middleware covers these paths globally, including error
and unexpected nested-path responses.

| Path | Authorization | Exact JSON body |
| --- | --- | --- |
| `/api/v1/game-auth/device-sessions` | `Bearer <normal PKCE access token>` | `{"protocol_version":1,"remember_device":true}` |
| `/api/v1/game-auth/device-sessions/native-characters` | `OterynDevice <device credential>` | `{"protocol_version":1,"client_id":"<Rust OAuth client UUID>"}` |
| `/api/v1/game-auth/device-sessions/tickets` | `OterynDevice <device credential>` | `{"protocol_version":1,"client_id":"<Rust OAuth client UUID>"}` |
| `/api/v1/game-auth/device-sessions/revoke` | `OterynDevice <device credential>` | `{"protocol_version":1,"client_id":"<Rust OAuth client UUID>"}` |

The device scheme uses exactly one ASCII space and the exact `OterynDevice` spelling.
The credential is accepted only in this Authorization header, never a request JSON
field or URL. The public client UUID is canonical lowercase; it is binding context,
not a confidential client secret. A device credential does not authenticate on any
Passport Bearer endpoint. Enrollment resolves the standard Passport `api` guard inside
the controller's sanitized exception boundary and then uses the locked core OAuth verifier.
It does not create a competing authenticator or accept a web cookie as native authority.

Enrollment response (HTTP 200):

```json
{
  "protocol_version": 1,
  "device_credential": "<opaque secret>",
  "family_id": "<Platform family UUID>",
  "absolute_expires_at": 1794132000,
  "idle_expires_at": 1792144800
}
```

All expiry fields are UTC Unix seconds as JSON integers. The family UUID is metadata,
not account/character authority. Rotation responses contain the same fields with the
new credential and original family/absolute deadline. The character response additionally
contains `characters`, whose entries preserve the owning native read contract's
`character_id`, `world_id`, `name` and `availability`. Its wrapper version is 1; this
does not change the original OAuth character endpoint's protocol version 2.

The ticket response additionally contains `ticket`, integer `expires_in` bounded by the
existing native ticket lifetime (at most 60 seconds), and integer UTC `expires_at`.
No OAuth token is minted or returned. The character callback uses the canonical owner's
existing projection with transaction locks and verifies projection state and JSON response
bounds before rotation commits. The native ticket callback is fixed in server code and
cannot issue Canary/legacy tickets. Responses are bounded to 16 KiB.

Revocation returns HTTP 200 with exactly `{"protocol_version":1,"revoked":true}`;
it does not rotate or reveal the owner/family state. Revoking again with the same correctly
bound credential remains idempotent.

Failures contain only an `error` field:

- HTTP 400 `invalid_request`: request shape/type/encoding/query rejection;
- HTTP 413 `invalid_request`: declared or actual body exceeds bounds;
- HTTP 401 `device_authorization_unavailable`: missing/wrong credential, owner/client/scope
  refusal, revoked/expired/replayed family or unusable native ticket authority;
- HTTP 429 `too_many_requests`: source throttle, with a positive `Retry-After`;
- HTTP 503 `device_authorization_unavailable`: disabled/production/transport gate,
  invalid configuration, unavailable projection/database or unexpected application failure.

No failure response echoes input, exception messages, credentials, account identifiers or
stack traces, including when application debug is enabled. Application exceptions within
the candidate controller are deliberately not reported with a credential-bearing request.
Deployment logging and tracing must still redact Authorization and successful credential
responses; these adapters do not qualify unrelated logging infrastructure.

A source throttle independently covers enrollment, reads, ticket issuance and revocation;
rotating a token cannot reset it. The default is 30 requests/minute and configuration must
be an integer in 1..60. This shared source policy is a candidate availability/security
tradeoff for players behind NAT, not a claimed final production abuse policy.

Plain HTTP is refused unless strict `allow_insecure_loopback` is true, environment is
testing/preproduction, request host is the literal `127.0.0.1`, both the raw transport
peer `REMOTE_ADDR` and effective request IP are literal loopback, and the complete request
origin exactly matches configured `APP_URL`. Different ports, `localhost`, remote hosts
or remote source addresses fail closed. A trusted remote proxy claiming a forwarded
loopback client cannot use this exception; neither can a local proxy describing a remote
client. HTTPS deployment behind a proxy depends on the
existing bounded trusted-proxy configuration; this batch does not alter it. The local
exception is false by default and is not a remote-HTTP or production exception.

## Validation boundary

The scoped Feature suite covers real PKCE enrollment ordering, unchanged OAuth-family
ticket consumption, explicit consent, one enrollment per bearer, scope/client/owner
binding, both generation changes, disabled/terminated accounts, client revocation, hashed
storage, real MFA confirmation invalidating pre-MFA devices/OAuth tokens, multiple
predecessor replay, durable terminal denial, expiry boundaries,
absolute-deadline preservation, transactional native-ticket rollback, logout/cancellation,
ambient transaction refusal, cross-database refusal and guarded migration rollback.

Those tests are restricted to isolated in-memory SQLite and exercise committed sequential
state transitions. SQLite does not prove production row-lock concurrency behavior.
Independent database races on the chosen deployment engine, endpoint throttling/redaction,
OS-vault restart/cross-process behavior, complete HTTP/client E2E and security review remain
required evidence before activation. This document must record actual runner results
separately from source capabilities; no test pass or production qualification is implied
by listing a case here.

`NativeDeviceSessionHttpTest` adds actual PKCE-to-HTTP enrollment, owner-scoped projection
read, native ticket issuance without new OAuth tokens, durable HTTP replay revocation,
idempotent logout, input authority/type/duplicate/size rejection, no-cache errors, source
throttle boundaries, strict transport/default/production gates, transactional projection
failure and generic unreported unexpected dependency errors. These are isolated actor-to-
HTTP-result tests, not deployment/browser/vault/game-world E2E proof.


Isolated source qualification on 2026-10-09: HTTP/core/MFA/cache suites pass
64 tests/657 assertions, affected Pint and scoped PHPStan level10 pass. This
includes enrollment followed by the original native OAuth ticket route consuming
both access and refresh credentials, followed by remembered continuation without
new OAuth tokens. Full-string JWT Bearer parsing and raw-plus-effective loopback
peer checks have regressions. These SQLite-memory results do not establish
deployment-database race safety or activate this candidate.
