### Authorization and approval

The permissions below are proposed grants for the named operation. The economy summary reuses the existing `game.economy.read` permission. [portal-rs/crates/admin/src/rbac/catalog.rs:219](../../portal-rs/crates/admin/src/rbac/catalog.rs#L219)

The actor labels describe eligible roles for explicit grants. The server authenticates the actor, resolves the allowed Game scope, and supplies the permission and risk classification. Staff sessions require MFA. Mutations require CSRF protection, a bounded reason code, and the cited case or change reference. The Game owner rechecks actor or issuer authority, target scope, relevant revisions, and execution fences before deciding. Automatic domain workers use the narrowly scoped service identity and carry the originating authorization evidence where applicable.

| Tier | Proposed approval rule |
| --- | --- |
| R1 | Scoped read and audit each page or exact read. No second approver. |
| R2 | Scoped, bounded change with a reason and case or change reference. No second approver. |
| R3 | R2 controls plus requester step-up within five minutes of issuance and dry-run support. No second approver unless a stricter domain rule applies. |
| R4 | R3 controls plus a Game dry run and approval from a second, independently scoped administrator. Bind approval to the exact intent, target, preview digest and expected revisions. Require approval less than 30 minutes old and approver step-up within five minutes of approval. Recheck prerequisites inside the approved execution window. |

These proposed staff rules follow the ADM risk thresholds and timing model. ### Request, outcome, replay and audit

- **Request.** Fields below supplement the operation/version, canonical target and actor or issuer scope, applicable reason and authorization evidence, correlation ID and relevant time/owner fence. Resolve opaque IDs against the named authority. Treat a world and channel as distinct identifiers. Validate closed action variants and recheck required revisions at the point of effect. A worker executes the immutable decision it received.
- **Outcome.** Echo the logical operation ID, scope and binding digest, with the authoritative state, decision time, safe result or typed refusal, and applicable owner epoch or recovery generation. A durable mutation receipt also carries a Game ledger or receipt reference. Show a queued request as pending. A timeout or lost receipt stays uncertain until reconciled by the original ID. Only a matching, current-generation terminal success receipt proves a Game effect. A terminal rejection proves no effect only when the authority guarantees it. Ambiguous or partial execution requires reconciliation. Check prior receipts and fences before resending.
- **Idempotency.** For new panel requests, a submission nonce scoped to the authenticated actor, operation and target maps atomically to one stable operation ID and the canonical intent digest. Return the stored operation on an exact retry. Conflicting reuse refuses and preserves the first binding. On Game, deduplicate by issuer and logical operation ID, with digest validation and a durable result committed with the effect. Distinct business steps use distinct operation IDs. A preview has its own identity and is linked to the approved execution. Use the native domain's existing idempotency key where specified below. Each read page has a separate audit identity, and delivery retries of that page reuse it.
- **Audit.** Append request or read, approval when applicable, dispatch and result events under the same correlation. Record actor/issuer ID, effective permission and scope, operation and logical ID, case/change reference, reason code, risk, approval identities and timestamps, binding and preview digests when applicable, decision time, redacted before/after revisions, result or refusal code and Game ledger/receipt reference. The operation sections add specific fields. Keep sensitive evidence as restricted references and scrub credentials, raw evidence content and unnecessary player data from logs and audit fields.
- **Refusals.** New panel profiles use `INVALID_INPUT`, `SCOPE_DENIED`, `UNSUPPORTED_OPERATION`, `STALE_REVISION` and `IDEMPOTENCY_CONFLICT` as applicable. `STEP_UP_REQUIRED`, `APPROVAL_REQUIRED`, `PREVIEW_STALE` and `WINDOW_CLOSED` cover applicable control failures. `SOURCE_UNAVAILABLE` and `RECONCILIATION_REQUIRED` describe unavailable or uncertain evidence and carry no terminal mutation claim. The codes are proposal vocabulary for new profiles and panel mappings. Use the existing code set verbatim on a native domain wire and explicitly version any new domain code. Operation-specific codes below supplement these rules.

## 1. Character world or channel transfer

- **Operation ID and authority.** `character.transfer.placement`. A scoped senior GM with `game.player.transfer.placement` requests a case-bound repair at **R4**, with independent approval and a transfer window. A character owner may request an eligible self-service transfer under a separate owner-bound variant with server-verified ownership, recent authentication, explicit consent and an eligible service reservation if paid. Treat the transfer effect as R4 in either variant and bind staff approval to the exact proposed move. Game-side owner is Character Authority with the source and destination placement/admission authorities. Ratify the product eligibility policy and capacity handling with those owners.
- **Request.** `account_id`, `character_id`, `expected_character_revision`, `expected_lifecycle_revision`, `from_world_id`, `target_world_id`, applicable source and destination `channel_id` values, `capacity_reservation_ref`, `transfer_policy_revision`, and consent or approved repair reference. Under the transfer fence, require durable offline status, validate both placements and resolve world-bound obligations before committing the move.
- **Response.** Prior and resulting canonical placement, `character_revision`, projection epoch/revision and transfer receipt. One CharacterId and one authoritative placement survive the move.
- **Idempotency and audit.** Map the submission key to one Character Authority `operation_id`. Bind owner consent or repair decision and capacity reservation to that ID. Audit source/destination, policy and reservation refs, obligation disposition summary and committed placement revision.
- **Refusals.** `CHAR_CMD_CHARACTER_IN_SESSION`, `CHAR_CMD_WORLD_NOT_ACCEPTED`, `CHAR_CMD_CHARACTER_NOT_TRANSFERABLE`, `CHAR_CMD_HOUSING_NOT_PREPARED`. A specific capacity or channel refusal would need a new wire version.
- **Extends.** Qualify the reserved world-transfer profile in the [character services wire](OTERYN_V2_CHARACTER_SERVICES_COMMAND_CONTRACT_PROPOSAL.md#L108-L124) under the [Character Authority profile](OTERYN_V2_CHARACTER_AUTHORITY_COMMAND_CONTRACT.md#L398-L409) and [topology identities](OTERYN_V2_WORLD_TOPOLOGY_CONTRACT.md#L26-L42). The Portal owner parser supports schedule, cancel and rename. The matrix tracks both owner and GM placement transfer as missing. ## 2. Character deletion finalization and status

- **Operation IDs and authority.** `character.deletion.finalize` names the Game-owned automatic effect at **R4**. Game-side owner is Character Authority. Its finalizer would require the committed schedule, elapsed authoritative grace, clearance of holds and approval of the finalization policy by two distinct Game lifecycle administrators. The worker would use a dedicated finalizer service grant. The policy-level approval for automatic execution requires owner acceptance. `character.deletion.status.get` gives a scoped GM with `game.player.deletion.status.read` an **R1** case read with no second approval.
- **Request.** The internal finalizer uses `character_id`, `account_id`, `deletion_operation_id`, `expected_character_revision`, authoritative `deletion_effective_at`, `retention_policy_revision` and `hold_decision_ref`. Revalidate under the same lifecycle fence as cancellation. The status read supplies subject IDs, schedule operation ID and case reference.
- **Response.** Finalization returns a private tombstone reference, terminal revision, effective and finalized times and disposition code. Status returns the Game-observed lifecycle, deadline, source freshness and tombstone reference when authorized. A local countdown only displays the schedule.
- **Idempotency and audit.** Key automatic finalization by `(character_id, deletion_operation_id)` and map it to one Game `operation_id`. Status uses a per-request read ID and echoes the schedule/finalization IDs when visible. Audit schedule and finalizer IDs, grace evidence, policy approval revision, hold decision reference and terminal revision.
- **Refusals.** `DELETION_GRACE_OPEN`, `DELETION_SCHEDULE_SUPERSEDED`, `DELETION_HOLD_ACTIVE`, `TRUSTED_TIME_UNAVAILABLE`, `DELETION_STATUS_UNAVAILABLE`.
- **Extends.** Add a private status/tombstone result to the [Character Authority deletion profile](OTERYN_V2_CHARACTER_AUTHORITY_COMMAND_CONTRACT.md#L390-L396), preserving the [character services decision for automatic Game finalization](OTERYN_V2_CHARACTER_SERVICES_COMMAND_CONTRACT_PROPOSAL.md#L120). ## 11. World maintenance, drain and restart

- **Operation ID and authority.** `world.maintenance.control`. A scoped Game operator or Game administrator with explicit action permission `game.world.maintenance.set`, `game.world.drain` or `game.world.restart`, **R4** for each action, with independent approval and a maintenance window. Game-side owner is World Runtime Operations and the fenced node supervisor for the target.
