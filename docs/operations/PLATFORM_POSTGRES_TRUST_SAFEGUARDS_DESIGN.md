# Platform PostgreSQL P6a: trust safeguards design note

Status: proposed, for acceptance before any P6a implementation. Governing plan: `PLATFORM_POSTGRES_MIGRATION_PLAN.md`, *P6 / Trust safeguards (P6a)*. Decision: ADR 0046. This note changes no code, configuration, schema, deployment, secret or data.

## Purpose and boundary

The first `game-auth:native-admission:publish-trust` attempt on the clean-slate PostgreSQL database advances the trust-state witness before its database transaction commits. A failed attempt can leave the missing-profile state: a trust-state floor of 1, no profile row, no database trace. `reconcile --trust` refuses it (`NativeEvidenceRecoveryReconciler.php:61-71`) and so does a new publication (`NativeSigningTrustRegistry.php:47-50`).

P6a adds only what the plan requires before step 4: a provenance-only init and durable attempt evidence. It adds no repair of the missing-profile state, never lowers, moves, edits or replaces the PostgreSQL witness, and reopens neither a rollback nor a P3 re-run.

## Mechanism

Items marked *proposal* are choices this note asks the reviewer to accept. Everything else restates the plan.

### 1. Provenance-only init

- A console command (*proposal*: `game-auth:native-evidence:init-provenance`, under the native evidence console commands) calls the witness's store-provenance path (`NativeEvidenceHighWaterWitness::reconcileStoreProvenance`) without entering a namespace. It creates the PostgreSQL witness-store id and its database binding, and advances no namespace floor.
- It runs only from `cutover-postgres.sh`, at the start of step 4, after the last rollback point.
- Idempotent on a consistent state: when the store id and binding already exist and agree, it changes nothing and succeeds.
- It refuses, and changes nothing, when the id and binding disagree, when only one of them exists, or when the witness directory holds anything it cannot classify. It never repairs by overwriting.

### 2. Attempt evidence

- Append-only records on host storage outside the database, outside the witness directory and outside the Platform volumes, so that no database or Platform volume restore rolls them back. *Proposal*: the new NAS host directory `/volume1/docker/oteryn/attempt-evidence/` (override `OTERYN_ATTEMPT_EVIDENCE_HOST_PATH`), one file per P6 run, created `0600`, written with `O_APPEND` and `fsync`, and set append-only (`chattr +a`) where the filesystem supports it. It is a plain host path, not a Docker volume, and is deliberately not the key-custody directory beside `used.kids` and not inside `oteryn-native-admission-keys`, `platform_storage`, `postgres_data` or the WAL spool, because the migration plan backs those up and a restore of any of them would roll the records back. The directory is excluded from every backup and restore task, and no restore task targets it. `cutover-postgres.sh` refuses to run the publication when the resolved real path lies inside any of those volumes or spool paths, or when the directory is not writable.
- Each record binds: the new P6 run id, the PostgreSQL witness-store id, the trust scope and the key id being published.
- Two records per attempt (*proposal*): `intent`, written and flushed before `publish-trust` runs, and `result` (success or failure), written after. An `intent` without a `result` means the witness may have advanced. If an `intent` cannot be written, `cutover-postgres.sh` does not run the publication.
- The evidence is a record for the operator and the owner. No code reads it to authorise a repair.

### 3. Order in step 4

1. Provenance-only init.
2. Record `intent` for this run id, store id, scope and key id.
3. Native admission on through the deploy: `publish-trust`, then `self-check`.
4. Record `result`.

On failure the plan's step 4 rules apply unchanged: native admission off, witness and database kept. The missing-profile state stops the cutover, which is not declared done. Native admission stays off, the scope stays unavailable, and the owner decides.

### 4. Repair

No repair is designed here and nothing in P6 depends on one. A future repair needs a proof that it tells a failed publication apart from a restore or relational data loss, its own review, and the producer contract owner's review before it is built. The attempt evidence is an input to such a proof, not the proof.

### 5. Invariants carried as tests

- A restore never synthesizes a profile.
- A successor key is new: generated by `generate-native-admission-key.sh`, present in `used.kids` exactly once as its own generation record, and absent from database history (`historicalKeyIdExists()`).
- Forward-only: no P6a path lowers, moves, edits or replaces the PostgreSQL witness.

## Expected paths

`app/GameAuth/NativeEvidence/` (provenance-only entry), the native admission console commands, `tests/Feature/GameAuth/`, and the step-4 call in `deploy/synology/scripts/cutover-postgres.sh` (owned by P6, not P6a). The implementation packet fixes the exact paths.

## Tests

| Case | Expectation |
| --- | --- |
| Init on an empty witness directory | Creates store id and binding, no namespace floor above 0 |
| Init repeated | No change, success |
| Init with id/binding mismatch or only one present | Refuses, nothing changed |
| Init followed by a first publication | Floor advances only through the publication |
| Evidence write fails | Publication not attempted |
| Attempt with `intent` only | Record binds run id, store id, scope, key id; no code path treats it as a repair authorisation |
| Failed first publication (missing-profile state) | `reconcile --trust` and a new publication still refuse; no profile created; witness unchanged |
| Restore simulation (database behind witness) | No profile synthesized (the plan's one negative test) |
| Successor key id | In `used.kids` once, not in database history |
| Any P6a path | Never lowers, moves, edits or replaces the witness |

## Open questions for the reviewer

2. Is the two-record `intent`/`result` shape acceptable, or is a single record preferred?
