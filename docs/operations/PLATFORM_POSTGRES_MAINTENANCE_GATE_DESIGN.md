# Platform PostgreSQL P6b: maintenance-gate state machine

Status: proposed, for owner acceptance before P6 starts. Governing plan: `PLATFORM_POSTGRES_MIGRATION_PLAN.md`, *P6 / Edge gate instead of maintenance mode*. Decision: ADR 0046. Governing issue: #1474. This note changes no workflow, script, configuration or data. It fixes the design that the later implementation (*Files and tests*) must follow and lists what the owner must approve (*Owner approval*).

## Fixed by the plan

- The gate is the two canonical tunnel ingress rules (`oteryn.molehill.cloud`, `gateway.molehill.cloud`) switched between their fixed loopback origins (`http://127.0.0.1:8000`, `http://127.0.0.1:8080`) and the Cloudflare `http_status:503` service. DNS records and the tunnel connector are not touched.
- The gate fails closed. No mutating entry point may reopen the origins except `maintenance-open`.
- `maintenance-close` and `maintenance-open` are new modes of the existing `Cloudflare Oteryn Endpoints` workflow (the workflow budget is full) and use the `apply` safeguards: confirmation phrase, fresh read, rejection of locally managed tunnels and ambiguous rules, preservation of unrelated rules and the final catch-all, re-read and hash check immediately before `PUT`.
- `maintenance-close` refuses, and changes nothing, when any other ingress rule has a service on port 8000 or 8080 of any host, or on any port of a local origin (loopback or the connector host itself).
- No maintenance bypass secret, cookie or path exists. The gate uses only the existing `production-cloudflare` environment and its token; this note adds no secret (`GITHUB_TOKEN` read access to Actions runs is not a new secret).
- Opening happens only in P6 step 7, or at the end of a rollback after `health-check.sh` passes on MariaDB.

## Decisions in this note

| # | Question left open by the earlier draft | Decision |
| --- | --- | --- |
| 1 | Where closure identity is stored | In a workflow artifact of the close run (`oteryn-edge-gate-closure`), bound to the edge by the tunnel configuration `version` that Cloudflare returns on every read. No new credential: the job only needs `actions: read` and uploads with the pinned `actions/upload-artifact` |
| 2 | Binding identity to a non-replayable edge generation | The open compares the live `version` to the `edge_version` recorded by the close. Any write after the close, including an external edit that restores identical closed rules, changes `version` and invalidates the closure |
| 3 | Serialization that cannot drop a close or open | One shared concurrency group for every mode that can `PUT` (`apply`, `maintenance-close`, `maintenance-open`), which guarantees that no two writes run at the same time, a read-only `guard` job that stops an `apply` before it can queue behind or replace a pending gate run, and a rule that a dropped or cancelled run can never read as success (see *Serialization*). No claim that GitHub queues without dropping |
| 4 | `apply` outside `open` | `apply` runs only when the fresh classification is `open`, and again only if the re-read immediately before its `PUT` still classifies `open`. In every other state (`closed`, `split`, `unknown`) it refuses with no write, because `apply` rebuilds both canonical rules with loopback origins and that would reopen the edge without gate evidence. Repair of a missing or wrongly pointed canonical rule is therefore not an `apply` job once the gate exists; see *Owner approval* |

## States

Derived from a fresh read of the tunnel configuration, never from memory of a previous run. Each rule is classified by its exact `service` value; a canonical rule must match by exact hostname, case-insensitively, with no path.

| State | Meaning |
| --- | --- |
| `open` | Both canonical rules on their fixed loopback origins |
| `closed` | Both canonical rules on `http_status:503` |
| `split` | Exactly one canonical rule on `http_status:503` and the other on its fixed loopback origin. Both rules change in one `PUT`, so only an external edit can cause it |
| `unknown` | Everything else: read failed, tunnel locally managed, rules ambiguous or missing, or a canonical rule on any service other than its fixed origin or `http_status:503` (including one rule on `503` and the other on an arbitrary service) |

The states are disjoint and exhaustive: `open`, `closed` and `split` are matched first by exact comparison, and whatever matches none is `unknown`. `split` and `unknown` never satisfy the external check and never count as open.

`audit` prints `gate_state=<state>`, `edge_version=<n>`, `other_origin_routes=<n>` (informational), `oteryn_bypass_rules=<n>`, `preserved_rules=<n>` and `preserved_rules_hash=<sha256>` (and `closure_match` when asked, below). Every dispatch `audit` run, with or without closure inputs, also uploads the result artifact `oteryn-edge-audit-result` (see *Evidence artifacts*). A closed gate is reported as bounded drift, not as failure, and audit's exit code semantics are unchanged (success whenever the state is safely readable).

## Mode contract

All new modes are `workflow_dispatch` only, from `main`, under `production-cloudflare`. The marker pull request and owner comment entry points stay limited to `audit` and `apply` and cannot request a gate mode. The `apply` guard lives in the script, so every entry point that reaches `apply` (dispatch, marker pull request, owner comment, and the push marker workflow `cloudflare-oteryn-endpoint-main-operation.yml`) is covered by one implementation.

### Inputs

| Input | Used by | Rule |
| --- | --- | --- |
| `mode` | all | Adds `maintenance-close` and `maintenance-open` to `audit`, `apply` |
| `confirmation` | all but `audit` | `maintenance-close`: `CLOSE-OTERYN-EDGE`. `maintenance-open`: `OPEN-OTERYN-EDGE`. Checked by the workflow and again by the script |
| `task_id` | both gate modes; optional on `audit` | Matches `^OTERYN-[0-9]{8}-[a-z0-9-]+$`. Names the cutover packet |
| `closure_run_id` | `maintenance-open`; `maintenance-close` when the fresh state is `closed`; optional on `audit` | Run id of the `maintenance-close` run that produced the current closure. A renewal close must name it (see step 3b); it is ignored for a close from `open` or `split` |
| `evidence_run_id` | `maintenance-open` | Run id of the cutover (`deploy-synology-staging.yml`) run that produced the cutover evidence |

### `maintenance-close`

1. Workflow boundary: ref is `main`, confirmation exact, `task_id` well formed.
2. Script: fresh read of token, tunnel (`config_src` must be `cloudflare`) and configuration; `validate_tunnel_config`; classify.
3. *Bypass precondition* (below). Refuses when `oteryn_bypass_rules` is not 0, with no write. Other rules do not block the close; they are preserved verbatim.
3a. *Fingerprint before the write.* A job `edge-fingerprint` (GitHub runner, no secrets, `needs: classify`) runs before the manage job, so the application is still reachable on an `open` gate. It requests the two canonical hostnames and, for a baseline, one random unused label under `molehill.cloud` (the parent of both canonical hostnames; the job has no secret and cannot read the tunnel configuration, so it knows no other wildcard parent), and uploads the small artifact `oteryn-edge-fingerprint-candidate` (`schema`, `collected_at`, per canonical host the HTTP status and the cookie names and response header names, minus a fixed generic list: transport and edge headers (`date`, `server`, `content-*`, `cf-*`), security headers (`strict-transport-security`, `x-frame-options`, `x-content-type-options`, `referrer-policy`, `content-security-policy`, `permissions-policy`, `x-powered-by`) and common framework cookies (`session`, `sessionid`, `csrftoken`, `jsessionid`, `phpsessid`), and minus names also present in the baseline). Only names are recorded, never values. The manage job downloads it from the same run and accepts it only when all of these hold: its own fresh classification is `open` (and the final re-read before the `PUT` is still `open`); neither canonical host returned 503 or an edge error; each canonical host yields **at least two distinct application-specific elements** (or the dedicated response marker below), otherwise that host's set is too weak and the status is `unavailable`; the schema, size and canonical-hostname-only content are valid. It then copies the set into `closure.json` with `fingerprint_status=collected`. In every other case from `open` or `split`, including a missing or failed fingerprint job and a `split` close (the application is not fully reachable), it records `fingerprint_status=unavailable` with a null fingerprint; the close itself still proceeds, because the authoritative guard is the API-side route check, and its wildcard and other-hostname probes are informational.
3b. *Renewal carries the fingerprint forward.* From `closed` the application is unreachable, so nothing can be collected and a renewal must never turn a known probe failure into an informational pass. The renewal therefore requires `closure_run_id`, fetches that closure artifact with the provenance rules of `maintenance-open` except for one narrow, renewal-only relaxation of the run conclusion, and requires its task, `edge_version` and `config_hash` to match the live closed configuration. It copies `fingerprint_status` and `origin_fingerprint` unchanged into the new `closure.json`, so `edge-probe` runs the same fingerprint check as the first close and fails again on the same foreign response. The relaxation exists because a close whose `edge-probe` failed ends with run conclusion `failure` although it wrote the gate and uploaded its closure. For a renewal only, the closure run may have conclusion `failure` if, per the run's jobs API, the manage job (which writes and uploads the closure) has conclusion `success`, `edge-probe` has conclusion `failure`, and every other job is `success` or `skipped`; the workflow path, event, branch, `run_attempt` 1, task and the single unexpired artifact rules are unchanged. Any other failed or cancelled run (the manage job failed or was cancelled, the artifact missing) is refused. `maintenance-open` and `audit` keep the strict `conclusion == success` rule, so a probe-failed closure can never authorize the open or satisfy the cutover precondition; only a later close run whose probes all pass can. A renewal with a missing, expired, duplicate, unreadable or mismatching previous closure is refused with no write: the gate stays `closed` and the operator investigates (a forgotten close run id is found from the run list; a closure lost to expiry or to a dashboard close needs the dashboard, as for an `unknown` edge). A known failed probe is fixed at its cause (remove the foreign route or proxy) and then the renewal passes; a previous `unavailable` stays `unavailable`, which was already the recorded assurance of that closure, never a stronger or weaker one.
4. Every successful close writes, so that it supersedes every earlier closure: for every state that proceeds, re-read immediately before the `PUT` and require the same hash, `version` and classification as planned (otherwise abort with no write, so an unrelated ingress edit made after the first read is never overwritten from a stale copy). State `closed` then `PUT`s the configuration built from that final read with the canonical rules unchanged (a renewal write whose only effect is a new `version`); state `open` or `split`: `PUT` the configuration in which only the `service` of the two canonical rules changes to `http_status:503` (every other field of those rules and every other rule is preserved byte for byte, in order, including the catch-all; the planned configuration must have the same `preserved_rules_hash` as the final read), then read back. State `unknown`: refuse.
5. Success requires the read-back to classify `closed`, the hash of the unrelated rules to equal the pre-write hash, `preserved_rules` and `preserved_rules_hash` to equal the pre-write values, and `version` to equal the pre-write `version` plus one (every successful close writes). Anything else is a failure, reported with the observed state, never as success; no closure is uploaded in that case, so a close that landed but failed this step is repaired from the dashboard, not by a renewal.
6. Upload `closure.json` as artifact `oteryn-edge-gate-closure` (retention 30 days): `schema` (`oteryn-edge-gate-closure/v2`), `task_id`, `close_run_id`, `run_attempt`, `edge_version`, `config_hash`, `preserved_rules_count`, `preserved_rules_hash`, `fingerprint_status` (`collected` or `unavailable`) and `origin_fingerprint` (null when unavailable). A renewal close from `closed` uploads it too, and its new `edge_version` makes every earlier closure and its evidence fail the open check (a second close can never leave an older closure usable). That is the recovery path after an ambiguous `PUT` when the earlier close run uploaded its closure (the renewal names it and carries its fingerprint forward). If that run died after the write and before the upload, the edge is `closed` with no closure to verify, the renewal is refused, and the way out is the dashboard (reopen, then close again); this keeps a known probe failure from being cleared by a renewal and is listed for owner approval.
7. Job order for a close: `classify`, then `edge-fingerprint`, then the manage job (the only one with secrets and the shared write group), then `edge-probe`. Job `edge-probe` (separate job, no secrets, runs on a GitHub runner outside the NAS): *External probes* below. The close counts as complete for the cutover only when the manage job and the probe job both succeed.

### `maintenance-open`

1. Workflow boundary: ref is `main`, confirmation exact, `task_id` well formed. `closure_run_id` and `evidence_run_id` are optional at this point.
2. Classify first. The script does a fresh read-only classification before any provenance work. State `open`: no write, no evidence and no provenance check (idempotent retry); go to step 6. State `split` or `unknown`: refuse (a `split` is an external edit, so the closure is no longer provable). State `closed`: continue.
3. Only for `closed`, `closure_run_id` and `evidence_run_id` must be present and numeric, and provenance is checked through `gh api` with the run's `GITHUB_TOKEN` (`actions: read`):
   - The closure run: workflow path `.github/workflows/cloudflare-oteryn-endpoints.yml`, event `workflow_dispatch`, branch `main`, conclusion `success`, `run_attempt` 1, exactly one unexpired `oteryn-edge-gate-closure` artifact.
   - The evidence run: workflow path `.github/workflows/deploy-synology-staging.yml`, event `workflow_dispatch`, branch `main`, `run_attempt` 1, exactly one unexpired `platform-cutover-gate-evidence` artifact, and either (a) `status == in_progress` (the run is still executing, so step 7 can live in the same run; the artifact is uploaded only at the exact point the evidence describes) or (b) `status == completed` with `conclusion == success`. The evidence artifact name is fixed and immutable, so a re-run (same run id, higher `run_attempt`) cannot publish fresh evidence and is refused; recovery after a failed open step is a new dispatch of the cutover or rollback with a new run id. This is a positive allowlist: every other combination (`failure`, `cancelled`, `timed_out`, `neutral`, `skipped`, `stale`, `action_required`, `queued`, `waiting`, a missing conclusion on a completed run) is refused. The closure run is held to the same rule in its strict form: `status == completed` and `conclusion == success`.
   - Contents: `closure.task_id == evidence.task_id == task_id`, `evidence.close_run_id == closure_run_id`, `closure.close_run_id == closure_run_id`, and `evidence.outcome` is `cutover_complete` or `rollback_verified`.
4. Script, still `closed`: require live `edge_version == closure.edge_version`, live `config_hash == closure.config_hash` and live `preserved_rules_hash == closure.preserved_rules_hash` on the classification read.
5. Re-read immediately before the `PUT`: the final read must again classify `closed` and match both `closure.edge_version` and `closure.config_hash` (a matching hash alone is not enough, because an external update that restores identical rules still raises `version`). Any mismatch aborts with no write. Then `PUT` the fixed loopback origins for the two canonical rules (all other fields and rules preserved) and read back; same success rule as the close, and the read-back `preserved_rules_hash` must equal `closure.preserved_rules_hash`.
6. In the same job, a fresh `audit` pass must show `gate_state=open`, `tunnel_contract=current` and current DNS; then job `edge-probe` proves the normal contract.

### Evidence artifacts

- `oteryn-edge-audit-result` (`audit.json`, retention 30 days): written by every `audit` run dispatched from `main`, open or closed, and only by it. Fields: `schema`, `audit_run_id`, `run_attempt`, `task_id` (or null), `closure_run_id` (or null), `gate_state`, `edge_version`, `config_hash`, `tunnel_contract`, `dns`, `other_origin_routes` (informational), `oteryn_bypass_rules`, `preserved_rules` (`count`, `hash`), `closure_match` (`yes`, `no` or `not_requested`); schema `oteryn-edge-audit-result/v2`. An open audit before the close has `gate_state=open` and `closure_match=not_requested`; an audit after the close carries the closure ids. No hostname other than the two canonical ones appears in it. The cutover takes the audit by run id (`audit_run_id`, passed by the operator) and never trusts the operator's words: it fetches the artifact with the open provenance rules (workflow path `.github/workflows/cloudflare-oteryn-endpoints.yml`, event `workflow_dispatch`, branch `main`, `status == completed` and `conclusion == success`, exactly one unexpired `oteryn-edge-audit-result` artifact), then requires the JSON `audit_run_id` to equal the run id, `task_id` to equal its own, the expected `gate_state` (`open` before the close, `closed` with `closure_match=yes` and its `closure_run_id` after it), `oteryn_bypass_rules=0`, a well-formed `preserved_rules`, and an age under 24 hours. Preflight records the open audit's `preserved_rules.hash`; every later audit (closed during the cutover, open at the unfreeze) must show the same hash, so the unrelated rules are proved byte-identical to the pre-close ones. It reads that JSON, never a log. The open audit is a cutover precondition only; it is not gate authority, because `maintenance-close` re-reads the edge itself.
- `oteryn-edge-gate-closure`: written only by `maintenance-close`, content above.
- `platform-cutover-gate-evidence` (`gate-evidence.json`: `schema`, `task_id`, `close_run_id`, `outcome`, `head_sha`): written by the P6 cutover run, and only (a) `cutover_complete` after step 6 is recorded done (step 5 native login smoke passed and the cutover is declared done; step 7 is the opening step, so it cannot be a precondition of itself), or (b) `rollback_verified` after the MariaDB rollback finished and `health-check.sh` passed against it. It names the `close_run_id` the cutover was run behind, so the operator passes that id into the cutover run. A closed gate with a stopped step (step 4 on ambiguous trust state, step 5 or 6 not recorded) produces no such artifact, so `maintenance-open` refuses and the gate stays closed.
- Neither file contains a secret, a hostname other than the two canonical ones, or configuration content. Run ids and hashes are logged in the summary.
- A retry needs fresh evidence by construction: after a rollback and a second close, the second close has a new `close_run_id`, so the first rollback's evidence does not authorize the open.

## Bypass precondition and preserved rules (shared tunnel)

Owner decision (cutover blocker fix, task `OTERYN-20261013-pg-cutover`): the tunnel is shared with the owner's unrelated services, so the gate cuts only the two canonical rules and **leaves every other ingress rule untouched**: verbatim, in its order, including the final catch-all, and with every top-level field. The earlier rule that `maintenance-close` and the cutover require `other_origin_routes=0` ("only two canonical ingress rules") is withdrawn. Other rules are never deleted, altered or reordered by the gate. Implemented once in the script and used in three places: `maintenance-close` (refuses on a bypass rule), `audit` (prints and records the counts and hash), and the cutover (see below).

- `other_origin_routes`: still computed with the rules below (any other rule whose service is an IP literal in any spelling, a local origin on any port, or port 8000 or 8080 of any host not on the allowed-host list) and reported as a count, but **informational only**; it no longer blocks anything.
- `oteryn_bypass_rules` (blocking, must be 0 for the close and in every audit the cutover accepts): the number of other rules that could still reach or shadow the Oteryn origins while the canonical rules return 503:
  - a service whose effective port is 8000 or 8080 on any host that is not on the allowed-host list (the Platform and Gateway origin ports; a DNS alias or LAN address is not trusted to be another machine), or a service that cannot be parsed (fail closed); `http_status:*`, `hello_world`, `bastion`, `socks5`, `socks-proxy` and `unix:` services never count;
  - a rule whose hostname, without a port and after normalization (lowercase, trailing dots stripped), is a canonical hostname, for example `oteryn.molehill.cloud:8443`;
  - a rule placed **before** a canonical rule whose hostname is empty (path-only), `*`, a `*.<suffix>` wildcard whose suffix matches a canonical hostname (cloudflared matches `*.<suffix>` by suffix), any other wildcard spelling, or not a string; ingress is first-match, so such a rule takes the canonical hostnames' traffic. After both canonical rules such rules cannot match them and do not count.
- `preserved_rules` / `preserved_rules_hash`: the count of rules other than the two canonical ones, and the SHA-256 of the canonical JSON (`jq -cS`) of the whole configuration with the two canonical rules removed (order and top-level fields kept). It is identical for the open and the closed configuration, so it proves the unrelated rules are byte-identical across the close, the cutover and the open.
- The allowed-host list is a fixed constant in the script and is empty by default. An entry is a deliberate, documented exception (hostname and reason in `CLOUDFLARE_ENDPOINT_MANAGEMENT.md`) that needs owner approval and a reviewed change; it is never an input.
- The same normalization applies to the canonical hostnames when the rules are classified (case-insensitive, trailing dot stripped).
- The results are counts and a hash only. Hostnames, services and ports of unrelated rules are never printed or written to an artifact, because the tunnel carries operationally sensitive topology.
- Cutover use: before the freeze, the cutover requires `audit` evidence for the same day: an `audit` run id from `main` whose `audit.json` has `gate_state=open`, `oteryn_bypass_rules=0` and a well-formed `preserved_rules`; it records `preserved_rules.hash` in its state at preflight. Every later audit it consumes (closed audits during the cutover, the open audit at the unfreeze) must show the same hash; a state with no well-formed recorded hash (written before this rule, or interrupted after the preflight step) is refused, never treated as a match. `maintenance-close` repeats the bypass check at close time on the same read it writes from, and the hash check at `PUT` proves that read is still current. A rule added between the audit and the close is caught by the close (bypass) or by the cutover (changed preserved hash).
- Accepted residual risk of the owner decision: an unrelated rule that routes to a local origin on another port (for example a local reverse proxy) is preserved and stays reachable while the gate is closed. If such a proxy forwards to the Platform, the Platform stays public. The API check cannot see behind the proxy; the `edge-probe` fingerprint is corroboration only. The operator confirms before the close that no preserved route proxies to the Platform or the Gateway.
- Cutover use after the close: the cutover does not trust the close run id alone. `audit` accepts optional `task_id` and `closure_run_id` inputs and, when given, fetches the closure artifact with the same provenance rules as `maintenance-open`, then compares the task, `edge_version` and `config_hash` to the live configuration. It prints and records (artifact `oteryn-edge-audit-result`, JSON, as for every audit) `closure_match=yes` only when the live state is `closed` and all three match, otherwise `no`. The cutover requires, before the freeze steps and again before it writes its evidence, a successful `audit` run from `main` (consumed by its run id as *Evidence artifacts* describes) with `gate_state=closed`, `closure_match=yes` and the same `closure_run_id` and `task_id` it was started with. After a second close the earlier `closure_run_id` yields `closure_match=no`, so the cutover stops. The cutover reads that JSON, never a log.
- Unverified residual risk, not detected by this design: a route to the loopback origins that does not pass through this tunnel (another connector, a host port forward). The plan keeps the host bindings loopback-only to prevent it, but the gate has no authoritative inventory of connectors or host forwards and claims no detection. The external probes below cover only the two canonical names, synthetic labels and the hostnames enumerated from this tunnel, so they cannot prove its absence. Closing this gap needs an authoritative inventory check, which is an owner decision (see *Owner approval*).

## External probes (`edge-probe` job)

Run on a GitHub-hosted runner, no secrets, only the two canonical hostnames plus synthetic names:

- After close: both canonical hostnames return HTTP 503 from the edge (`server: cloudflare`). For a random unused label under `molehill.cloud` and for the other tunnel hostnames, the probe fails only if the response is recognizable as a Platform or Gateway application response. It does not fail on every 2xx or 3xx, because the tunnel may legitimately carry other applications. A wildcard parent outside `molehill.cloud` is not identifiable by the secret-free probe job, so such a wildcard is not probed and counts as informational (an accepted residual risk below). Hostnames of other tunnel rules are probed from inside the job without being printed; only a count and pass/fail are logged.
- Recognizing an application response: the fingerprint is collected before the `PUT`, by the `edge-fingerprint` job in step 3a of `maintenance-close` (cookie names and distinguishing response header names of the two canonical hostnames while the gate is `open`), verified by the manage job and written to the closure artifact as `origin_fingerprint`. The `edge-probe` job reads it from this run's closure artifact. After the close, a probe response fails only when it carries **all** elements of one canonical host's recorded set (at least two distinct application-specific names, or the dedicated marker alone); a response that shares one common cookie or header name with the application is not a match, so a legitimate unrelated app cannot fail a close on a generic name. This is corroboration: the authoritative guard is the API-side bypass check, which rejects any other route on port 8000 or 8080 regardless of host and any rule that shadows a canonical rule. If `fingerprint_status` is `unavailable` (no stable distinguishing set, a split close, or a failed collection; a renewal inherits the status of the closure it renews), the wildcard and other-hostname probes are recorded as `informational` and cannot fail the run, and that fact is logged; the implementation must verify the fingerprint on the live open state first, and a dedicated application-side response marker header (for example `X-Oteryn-Origin`, a later, separate code packet) is an optional owner decision, not assumed here; when it exists and is present in the open-state response, the marker alone is a sufficient fingerprint and the composite rule is not needed.
- After open: neither canonical hostname returns 503, and the documented success endpoint of each answers per the cutover smoke definition. The path and content of those checks are defined by P6; this gate requires only the non-503 result and a green job.
- The probes are samples of this tunnel's own names. A pass is evidence for those names only, never proof that no other route to the origins exists.
- A failed probe fails the workflow run. It never triggers an automatic gate change.

## Serialization

A GitHub Actions `concurrency` group keeps at most one pending run and replaces an earlier pending one, even with `cancel-in-progress: false`. This note claims no lock stronger than that. The mechanism:

1. Every job that can `PUT` runs in one job-level group, `cloudflare-oteryn-edge-write`, with `cancel-in-progress: false`: the `maintenance-close`, `maintenance-open` and `apply` jobs, on every entry path. GitHub runs at most one job of a group at a time, so an `apply` and a gate write can never be in flight together. That removes the interleaving in which an `apply` reads version N, a close writes N+1 and the `apply` then writes N+2 and reopens the origins; Cloudflare has no conditional write, so mutual exclusion is the only strong fix. No read-only job (`classify`, `guard`, `audit`, `edge-fingerprint`, `edge-probe`) is ever in the group.
   - What the group cannot do is keep a pending run: it holds one pending run and replaces an older pending one. To keep an `apply` from replacing a pending gate run, every `apply` path starts with a read-only `guard` job (no environment, no Cloudflare secret, `actions: read`) that lists the runs of both endpoint workflows through the Actions API and fails, so the `apply` job never starts, while a `maintenance-close` or `maintenance-open` run is `queued`, `waiting`, `pending` or `in_progress`, or if the list cannot be read. The `apply` job `needs: guard`.
   - Dispatch: `mode` is an input, so the `manage` job's group is an expression on `inputs.mode`: the shared group for `apply`, `maintenance-close` and `maintenance-open`, a per-run group for `audit`; the dispatch `apply` has the same `guard` job.
   - Marker pull request, owner comment and push marker (`marker-manage`, `comment-manage`, and `operate` in `cloudflare-oteryn-endpoint-main-operation.yml`): the mode is only known after the marker is read. Each is split into a read-only `classify` job (no environment, no Cloudflare secret, `contents: read`) that applies the existing exact-marker checks and outputs `mode` (`audit`, `apply` or `none`), then an `audit` job (per-run group) or `guard` followed by an `apply` job in the shared group. An audit marker never enters the shared group.
   - **Residual window, stated plainly.** The `guard` and the group together cannot be atomic: if an `apply` passes its `guard`, and a gate run is dispatched and goes pending behind a running write before the `apply` job reaches the group, the `apply` job can replace that pending gate run. The effect is fail closed and visible: the replaced run is `cancelled`, a dropped close stops the cutover before the freeze, a dropped open leaves the gate closed, and the operator repeats it. It cannot reopen the origins by itself, because an `apply` only runs from `open` and re-reads before its `PUT`. The operator dispatches gate modes one at a time and not while a marker merge or comment `apply` is in flight (item 5); the `production-cloudflare` environment reviewer is the second control. This residual is listed for owner approval.
   - Test: the shared group appears on exactly the `apply`, `maintenance-close` and `maintenance-open` jobs and on no `audit`, `guard`, `classify` or probe job; every `apply` job `needs: guard`; the `guard` fails on a queued, waiting, pending or in-progress gate run and on an unreadable list; in the mock, an `apply` that read version N before a close wrote N+1 cannot run its `PUT` concurrently (the jobs are serialized and the second re-reads N+1 and refuses); a replaced pending gate run is `cancelled` and yields no closure or open record.
2. The cancelled run is visible: GitHub marks a replaced pending run `cancelled`. A cancelled, failed, timed-out or missing run never produces the closure or the open record, and the cutover treats it as not done.
3. The cutover proceeds only on positive proof, never on dispatch: a successful close run with the closure artifact, followed by the fresh `audit` showing `gate_state=closed`. A dropped `maintenance-close` therefore stops the cutover before the freeze instead of leaving the origins silently open.
4. A dropped `maintenance-open` leaves the gate closed (fail closed) and is repeated.
5. One dispatcher: while a cutover is in progress only the operator dispatches mutating modes, one at a time, waiting for each to finish. The pre-`PUT` hash check and the post-`PUT` `version` check detect any write by another party; the remaining window between the last re-read and the `PUT` is a bounded residual of the Cloudflare API (no conditional write is assumed), detected after the fact and reported as failure.

## Transitions

| From | Entry point | To | Rule |
| --- | --- | --- | --- |
| `open` | `maintenance-close` | `closed` | Bypass precondition passes, one `PUT` that preserves every other rule, read back, closure artifact, probes |
| `closed` | `maintenance-close` | `closed` | Needs a verified previous `closure_run_id`; fingerprint carried forward; renewal write (identical config, new `version`); new closure artifact; every earlier closure is superseded; probes |
| `split` | `maintenance-close` | `closed` | Completes the close |
| `closed` | `maintenance-open` | `open` | Classify first; then provenance and evidence checks, final read matching `edge_version` and `config_hash`, one `PUT`, read back, fresh `audit`, probes |
| `open` | `maintenance-open` | `open` | No write, no evidence; fresh `audit` and probes |
| `split` | `maintenance-open` | unchanged | Refuses |
| `unknown` | either mode | unchanged | Refuses, no write |
| `closed`, `split` or `unknown` | `apply` | unchanged | Refuses before any tunnel or DNS write, no warning-only path |
| `open` | `apply` | `open` | Existing behaviour; the re-read before the `PUT` must still classify `open` |
| any | DNS operations | unchanged | They never touch the two rules; `apply` DNS work is part of `apply` and stops with the same refusal |

## Failure and rollback behaviour

| Event | State afterwards | Handling |
| --- | --- | --- |
| Read, validation or bypass check fails before the `PUT` | Unchanged | Nothing written; fix and re-dispatch. A failed close before the freeze means the cutover does not start |
| Hash, `version` or classification mismatch at `PUT` time (close, renewal, open or `apply`) | Unchanged | No write; re-run from a fresh read |
| Transport failure or no response on the `PUT` | Unknown until read | No in-run retry (existing policy). Run `audit`. If the edge is still `open` or is `split`, re-dispatch `maintenance-close`. If it is `closed`, the earlier run died before uploading a closure (no closure to verify), so the renewal path is refused and the repair is a dashboard action (reopen, then close again) |
| A close's probe fails (for example a Platform response from a reverse proxy on another host) | `closed` | The run fails; the gate stays closed. The renewal carries the fingerprint forward and the same probe fails again until the cause is removed; it cannot clear the failure |
| Renewal without a verifiable previous closure | `closed` | Refused with no write (missing, expired, duplicate, mismatching or unreadable `closure_run_id` artifact); dashboard action if the artifact is gone |
| Fingerprint collection fails or finds the gate not open | Unchanged | The close proceeds with `fingerprint_status=unavailable`; the wildcard and other-hostname probes are informational and the API-side route check stays authoritative |
| Read-back disagrees, or `version` is not pre-write plus one | As read back | Run fails with the observed `gate_state`; never success. If the close landed (`closed` read back, or the read-back itself failed), no `closure.json` was uploaded because step 5 precedes step 6, so a re-dispatch from `closed` is refused (step 3b) and the repair is the documented Cloudflare dashboard action (reopen, then close again), not a renewal. If the observed state is `open` or `split`, re-dispatching `maintenance-close` converges |
| Runner dies before / after the `PUT` | Unchanged / new state | Before the `PUT`: re-running the same mode converges. After a close `PUT` and before the closure upload: the edge is `closed` with no closure, so a close re-run is refused (step 3b) and the repair is a dashboard action, as above. If the closure was uploaded and only the probe or a later step died, a close re-run is a renewal naming that `closure_run_id`. An open re-run after its `PUT` is a no-op |
| `maintenance-open` fails or is refused | Stays `closed` | Fail closed. Refused for missing, expired, unreadable or unbound evidence, a stopped cutover step, or evidence from another task or another closure |
| Open landed but audit or probe fails | `open` | The run fails and reports it. No automatic re-close: the operator decides to investigate or to start a new closure |
| Cutover script dies with the gate closed | `closed` | Stays closed until `maintenance-open` runs in step 7 or at the end of a rollback |
| Gate state changed by the Cloudflare dashboard or API outside the workflow | `split`, `unknown`, or `open` | Classified from the fresh read. A closure whose `version` no longer matches cannot authorize an open |

There is no automatic gate rollback and no automatic reopen. The application rollback (P6 step 3 and the failure branches) comes first, `health-check.sh` passes on MariaDB, then `maintenance-open` runs with `rollback_verified` evidence. The only bypass of the gate is the owner editing the two canonical rules in the Cloudflare dashboard (break-glass, as `CLOUDFLARE_ENDPOINT_MANAGEMENT.md` already allows for incorrect canonical values). It is outside the workflow, must be recorded in the cutover evidence, and is the expected route when a closure can no longer be proven (for example a `split` state, or a no-op dashboard save after a completed cutover). Re-closing creates a new closure that needs fresh evidence.

## Accepted residual risks (owner, 2026-10-12)

The owner accepted the residual risks of this design ("akceptuje ryzyko"). This section is the home for every edge case that cannot be removed fully; later review findings of that kind are recorded here instead of triggering a redesign. A concrete internal inconsistency or defect is still fixed in the note.

| Residual risk | Why it remains | Mitigation kept |
| --- | --- | --- |
| Sub-second window between the last re-read and the `PUT` | Cloudflare has no conditional write (no `If-Match`) | Hash and `version` re-read immediately before the `PUT`, one running write at a time through the shared write group, post-write `version` and read-back checks, one dispatcher |
| An `apply` that passed its `guard` can replace a gate run that went pending behind a running write | GitHub concurrency keeps one pending run and replaces the older one; no durable lock exists | Read-only `guard` before every `apply`; the replaced run is visibly `cancelled`; fail closed (a dropped close stops the cutover before the freeze, a dropped open leaves the gate closed); `apply` only runs from `open` |
| A route to the origins outside this tunnel (host port-forward, another connector), and a remote name that resolves to the connector on a non-protected port | The tunnel API cannot see them | Probes are samples of this tunnel's names only and make no detection claim; connector and port-forward inventory is left to the owner |

| A closed edge whose closure was lost (run died after the `PUT`, or the 30-day artifact expired) | A renewal needs a verifiable previous closure | Repair is a dashboard action (reopen, then close again) |
| The dashboard is the only bypass of the gate and the repair path for an `unknown` edge | Dashboard edits are outside the workflow's control | Every state is re-classified from a fresh read; hash and `version` checks detect the change |
| Legitimate remote origins must use a DNS name or an owner-approved allowed-host entry | IP-literal hosts and local origins are refused by default | Empty-by-default allowed-host list, reviewed change |
| A wildcard rule under a parent domain other than `molehill.cloud` is not probed | The secret-free `edge-fingerprint` and `edge-probe` jobs cannot read the tunnel configuration, and a read-only discovery job was judged not worth a second token path | The API-side bypass check (any port 8000/8080 rule refused, and any wildcard placed before a canonical rule that matches it) stays authoritative; a preserved route to a local proxy on another port is an accepted residual risk (owner decision) |
| Reliance on the `production-cloudflare` environment reviewer | A reviewer approves each gate run | Confirmation phrases and the one-dispatcher rule |
