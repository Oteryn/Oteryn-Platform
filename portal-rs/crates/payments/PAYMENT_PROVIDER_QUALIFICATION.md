# GAP-41 payment provider qualification

Live provider activation is pending provider selection and approval. The Platform can rehearse checkout, payment verification, wallet credit, refunds and reconciliation in testing or preproduction using the sandbox provider. Keep sandbox credentials and data separate from any live provider.

## Platform rehearsal

- Set `OTERYN_ENV` to `testing` or `preprod` and set `OTERYN_PUBLIC_ORIGIN` to the portal origin. Enable `PORTAL_COIN_PURCHASES_ENABLED` with a valid `PORTAL_COIN_PACKAGES` catalogue. Both the flag and an environment that permits sandbox payments are required. Enable `PANEL_PREMIUM_PAYMENTS` to show payment history and printable receipts.
- Enable `PORTAL_PAYMENTS_PROVIDER_WEBHOOK_ENABLED` separately and supply a disposable `PORTAL_PAYMENTS_PROVIDER_WEBHOOK_SECRET` of at least 32 bytes. Use the exact timestamp and raw body signature in the provider webhook contract. Turning checkout on does not configure the signed webhook. Never share the signing material or include it in qualification evidence.
- Sign in as a verified player and open **Sandbox coin checkout** from Account or Payments. Select a package, confirm the server quote and complete the test payment. Reopen the order from the account list. Record the order ID and the payment intent ID from Payments. Confirm the paid state, matching amount and receipt, and one wallet credit. A declined payment should leave a failed order with no wallet credit.
- Sign in as staff with MFA, `admin.access` and `payments.reconcile`. In **Commerce → Payment qualification**, look up the exact payment intent ID. Check order state, receipt, and credit. For browser Store test-bank top-ups, also check the wallet delivery job. Use the existing reconciliation form to record a reviewed payment when appropriate. The review leaves the ledger state intact.
- Deliver a signed full refund for that sandbox order using the stored provider reference. Check the debited amount, refunded state and recorded provider outcome by event ID. Redeliver the same event and confirm replay acknowledgement and a single debit. An unsigned event, malformed payload, or wrong reference, currency or amount must produce no wallet effect. A second full refund with another event ID must also produce no further debit.
- Rehearse a temporarily unavailable database or wallet. After recovery, retry the same event ID and bytes with a fresh timestamp. Verify one committed effect. Rehearse a refund after coins have already been spent and inspect the resulting review flag and hold. Use the existing staff player tools to review or resolve a hold.
- For the separate staff refund queue, an uncertain provider result should remain pending reconciliation. Inspect the payment and refund-job states before using `oteryn-portal commerce-refunds-reconcile --dry-run --actor <staff-id>`. The existing command can requeue the same job and preserve the provider idempotency key. An exhausted job or an approved refund request alone does not prove that funds were returned.

The full browser rehearsal is `portal-rs/e2e/specs/gap-41.spec.mjs` in the stock local runner. Supply a disposable webhook secret and a valid package catalogue to the launcher before starting it. For example, one catalogue entry can have ID `01934f10-7c02-7001-805b-3b1122334402`, title `Sandbox coins`, 500 coins, `price` of `{"minor_units":499,"currency":"EUR","exponent":2}` and `valid_for_seconds` of 120. See the runner README for launcher and test commands. With the standard unconfigured checkout and webhook, the spec checks refusal for those paths and uses the existing Store test bank to prove staff payment lookup.

## Activation decision and remaining ownership

Provider selection must establish the production checkout and refund APIs, signature verification and event mapping, authenticated settlement evidence, idempotency and recovery after provider timeouts, and reconciliation against provider reports. Before activation, obtain approval and qualify the chosen provider's sandbox for success, decline, duplicate delivery, uncertain results, refunds and chargebacks. Define custody and rotation, payout reconciliation, operational ownership and the rollback decision. Show provider and environment qualification evidence before enabling real payment effects.

The account-only rehearsal uses the Platform ledger and requires no Game input. Game must separately qualify its native client checkout handoff, display of authoritative balance and order revisions after a settlement or reversal, and any behavior that spends or delivers Game assets using that balance. Character-scoped requests still depend on existing authoritative ownership checks and return unavailable when that authority is unavailable.
